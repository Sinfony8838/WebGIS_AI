## 为什么原来没能删除

用户原句是“删除当前所有打开的图层”。旧规则按包含关键词判断动作，把修饰目标的“打开”当作显示操作，随后因无法匹配单个图层而要求澄清。该分支提前结束了规划。与此同时，手动删除虽然存在，助教的工具注册表和执行器没有对应的删除能力，所以改提示词或更换模型并不能补齐整条链路。

补齐工具后的真实 MiniMax-M3.1-Flash 测试又发现：带“保留人口分布、保留隐藏胡焕庸线”约束的请求只产生口头确认，没有 actions。现在明确区分模型提交删除计划与服务端执行删除：模型输出真实 layer_ids，服务端冻结对象、展示清单，用户点击确认后才执行。

## 修复后的行为

1. 完整句规则解析动作、对象和参数。“删除当前所有打开的图层”只选择当前项目 visible=true 的图层，模型调用为 0。复杂约束完整交给模型，不先执行其中一个关键词。
2. delete_layers 在模式策略、参数校验和权限执行中注册，Chat 无权调用。仅删除项目图层及其引用，数据库源数据、素材和底图保留。
3. 确认清单冻结 ID 和图层版本。等待期间新增图层不进入清单；目标被改动或移除则整批失效，不误删新对象。
4. 确认采用原子状态变更，重复点击和并发确认最多执行一次；过期、篡改、跨项目、取消请求均不执行。
5. 含重复删除、创建后删除、同一目标先修改再删除的相互冲突计划在执行前拒绝，避免冻结版本被本计划自身作废。
6. 浏览器收到 sync_project 后检查当前列表、二维缓存和三维对象（包含未完成的异步加载）均已移除，再回传 applied。缺回执记录 partial，历史消息也更新为“界面尚未确认”，不重复删除、不假报全部完成。
7. 确认任务继承规划用量；等待确认不增加模型总结请求。前端确认任务接入取消、模式/项目/会话隔离和防重复提交。

## 使用流程

Operate 输入“删除当前所有打开的图层”，核对数量和名称，再点击“确认”。若要包含隐藏图层，应明确说“删除当前所有图层”；若要保留特定对象，完整说出约束。确认等待期间如修改了待删图层，重新提出删除请求即可生成新清单。
